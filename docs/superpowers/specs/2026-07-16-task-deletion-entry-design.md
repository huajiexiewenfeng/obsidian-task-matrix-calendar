# 任务编辑弹窗删除入口设计

**日期：** 2026-07-16  
**状态：** 用户已确认交互方案，等待书面规格复核  
**关联规格：** `2026-07-15-task-center-visual-import-redesign-v2.md`

## 1. 背景

插件已经具备新建、编辑、任务回收站和 `TrashService.moveToTrash()`，但当前任务中心没有删除入口。用户明确要求任务的添加、修改和删除都在插件内完成，因此现有界面尚未覆盖完整任务生命周期。

## 2. 方案比较与选择

评估了三个入口：

1. 编辑弹窗底部左侧：删除属于低频危险操作，和任务详情、保存动作处于同一上下文，卡片界面保持克制。
2. 任务卡片操作区：操作更直接，但会提高每张卡片的视觉噪声，也容易误触。
3. 任务卡片右上角菜单：界面最简洁，但增加一层隐藏操作和菜单状态。

用户选择方案 1。

## 3. 界面与交互

- 仅在编辑任务时显示“删除任务”；新建任务弹窗不显示。
- 删除按钮位于固定底部操作区左侧，取消和保存继续位于右侧。
- 删除按钮使用 Obsidian 危险操作语义和主题变量，不引入硬编码颜色。
- 点击“删除任务”后打开二次确认弹窗，显示任务标题并说明父任务的子任务会一同移入回收站。
- 二次确认提供“取消”和“移入回收站”。取消不产生写入。
- 确认成功后关闭确认弹窗和编辑弹窗，任务中心由索引更新自动刷新。
- 确认失败时保留编辑弹窗，恢复按钮可用状态，并显示具体错误；不能显示虚假的成功提示。

## 4. 任务与回收站规则

- 删除调用现有 `TrashService.moveToTrash(taskId, deletedAt)`，不直接删除 Markdown。
- 父任务和一层子任务作为完整 Markdown 块整体进入可见回收站。
- 子任务不能独立删除；界面不提供子任务独立删除入口，服务边界继续拒绝该操作。
- 删除前仍执行现有指纹冲突检查；任务被外部修改时拒绝删除并保留原文。
- `deletedAt` 使用实际确认删除时的 ISO 时间，而不是打开编辑弹窗的时间。
- 不改变标准任务 Markdown 格式、回收站格式或恢复逻辑。

## 5. 组件边界

- `TaskFormModal` 负责显示编辑态删除入口、管理待提交状态和错误反馈。
- 独立的删除确认弹窗负责危险操作确认，不在表单中复用普通保存提交。
- 表单服务端口增加删除能力，由插件装配层把现有 `TrashService` 适配给表单。
- `TrashService`、任务仓库和索引继续负责写入安全、回滚及刷新，不把持久化逻辑放入 UI。

## 6. 并发和错误处理

- 删除确认提交期间，确认弹窗的取消和确认按钮均禁用，防止重复执行。
- 同一删除动作最多调用一次 `moveToTrash()`。
- 指纹冲突、任务不存在、回收站写入失败或源文档删除失败均显示原始可读错误。
- 删除失败不关闭编辑弹窗，不修改表单字段，不产生成功提示。
- 如果回收站先写入而源任务删除失败，继续依赖 `TrashService` 现有回滚删除回收站条目的行为。

## 7. 测试与验收

自动化测试必须证明：

1. 新建模式没有删除按钮，编辑模式有删除按钮。
2. 点击删除只打开确认，不立即写入。
3. 取消确认不调用删除服务。
4. 确认时携带任务 ID 和确认时刻，且只调用一次。
5. 删除处理中按钮锁定，成功后关闭两个弹窗。
6. 删除失败时编辑弹窗保持打开、按钮恢复并显示错误。
7. 现有新建、编辑、取消、日期和四象限测试继续通过。
8. `TrashService` 的父子块整体移动、冲突保护和失败回滚测试继续通过。

真实 Obsidian 验收必须确认：

- 删除入口不会挤压或遮挡弹窗底部的取消、保存按钮。
- 明暗主题下危险按钮和确认信息均可读。
- 只做取消路径烟雾测试；除非用户明确准备了测试任务，否则不执行真实删除写入。

## 8. 非目标

- 本轮不新增回收站列表页、批量删除或永久删除入口。
- 本轮不改变恢复、清空回收站和保留策略。
- 本轮不允许子任务独立删除。
- 本轮不改变任务卡片操作区或右上角菜单。

## 9. 规格自检

- 无占位符或未决交互。
- 删除入口、确认、成功、失败和并发状态均有明确行为。
- UI、服务和持久化职责保持分离。
- 范围仅补齐插件内删除入口，不扩展回收站管理功能。
