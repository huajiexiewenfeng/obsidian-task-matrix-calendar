# Obsidian 任务中心视觉与旧任务导入重设计 V2

**日期：** 2026-07-15  
**仓库：** `<workspace>/obsidian-task-matrix-calendar`
**状态：** 用户已确认设计，等待书面规范复核  
**关联规范：** `2026-07-15-obsidian-task-center-interaction-import-redesign.md`

## 1. 背景与问题

现有插件已经具备统一任务/日历工作区、任务表单和旧任务迁移能力，但真实 Vault 冒烟验证暴露出三个问题：

1. 搜索框与项目、状态、截止风险、来源筛选以原生表单平铺，缺少清晰的信息层级，视觉上不像完整工作区。
2. 新建和编辑弹窗将字段连续纵向堆叠，分组不足、滚动过长，主要内容与执行属性没有主次关系。
3. 旧任务迁移会自动扫描配置根目录下的全部 Markdown。当前识别器把日期标题下的项目符号、编号、`P0-P4` 和状态文字组合成候选，导致大量普通笔记被猜测为任务；预览又没有优先解释数据来源和识别原因，用户无法建立信任。

本规范覆盖上述界面和迁移识别问题。现有标准任务 Markdown 格式、任务状态机、四象限约束、日历联动、指纹冲突保护和 Markdown 单一事实源保持不变。

## 2. 已选择的方案

用户通过可视化比较确认：

- 工作区视觉：B「沉静工作台」。
- 新建/编辑弹窗：B「分组单栏」。
- 旧任务识别范围：手动选择文件；复选框自动识别，普通列表作为默认不选中的候选。
- 导入界面：A「三步导入向导」。

未采用的主要方案及原因：

- 原生紧凑工具栏：空间效率高，但整体层级弱于沉静工作台。
- 筛选抽屉：默认更干净，但常用筛选多一次操作。
- 双栏任务表单：桌面端无需滚动，但窄 Obsidian 窗格适配较差。
- 两步任务向导：单步轻量，但频繁创建任务时多一次点击。
- 单页迁移预览：审阅效率高但信息密度过大，重复现有可用性问题。
- 文件/详情分栏迁移：适合高频批处理，但对首次导入不够直观。

## 3. 工作区视觉设计

### 3.1 顶部层级

工作区顶部从上到下分为三层：

1. 标题与主操作：左侧显示任务中心标题或轻量上下文文案，右侧仅突出“新任务”。“导入旧任务”使用次级按钮。
2. 模式导航：任务矩阵与日历使用分段式主切换，当前模式有明确选中态。
3. 搜索与筛选：搜索框占主要宽度；项目、状态、截止风险、来源显示为带当前值的轻量筛选胶囊。

当任一筛选偏离默认值时：

- 对应胶囊使用主题强调色。
- 工具栏显示“清除筛选”。
- 清除操作一次恢复默认活动任务视图，不改变任务/日历模式。

搜索范围继续包含标题、详情、项目和标签。输入搜索词时必须保持焦点与光标位置。

### 3.2 主题与响应式

- 颜色、边框、背景、阴影、文字和交互状态全部使用 Obsidian CSS 变量。
- 不硬编码浅色或深色主题颜色；插件随 Obsidian 明暗主题切换。
- 宽窗口中筛选胶囊同行展示；空间不足时自然换行。
- 窄窗口中标题、主操作和模式导航分行，但搜索仍位于筛选项之前。
- 所有按钮、输入框、筛选项提供可见的键盘焦点状态。

## 4. 新建与编辑任务弹窗

创建和编辑共用一个分组单栏表单，差异仅来自标题、初始值和最终服务调用。

### 4.1 字段分组

1. **任务内容**
   - 任务标题，必填。
   - 详情，支持多行文本。
2. **执行安排**
   - 状态。
   - 四象限。
   - 开始日期。
   - 截止日期。
3. **项目与标签**
   - 默认折叠。
   - 展开后显示项目和标签输入。

弹窗底部为固定操作区，包含取消和保存/创建按钮。正文滚动时操作区保持可见。

### 4.2 默认值与规则

新建任务默认值：

- 状态：待办。
- 四象限：未分类。
- 开始日期：打开弹窗当天。
- 截止日期、项目、标签、详情：空。

日期接受 `YYYYMMDD` 和 `YYYY-MM-DD`，保存前统一规范为 `YYYY-MM-DD`。标题为空、日期无效或最终任务违反“非待办任务必须完成四象限分类”时，在对应分组内显示错误并阻止保存。

编辑任务必须允许显式清空开始日期、截止日期、项目、标签和详情。取消或关闭弹窗不得产生写入。

## 5. 旧任务导入规则

### 5.1 数据来源边界

点击“导入旧任务”后不再立即扫描整个任务根目录。第一步必须由用户从配置扫描目录内明确选择一个或多个 Markdown 文件。

候选识别规则：

1. Markdown 复选框 `- [ ]`、`- [x]` 及等价项目符号形式产生候选，并默认选中。
2. 普通无序列表和有序列表产生候选，但默认不选中。
3. `P0-P4`、完成、进行中、暂停等标记只补充已识别列表项的优先级或状态，不得单独把普通段落变成候选。
4. 最近的合法日期标题可以推断开始日期，但日期标题不决定一行是否成为候选。
5. 已经符合插件标准格式的受管任务块必须排除，避免重复导入。

### 5.2 候选证据

每条候选必须显示：

- Vault 相对来源路径。
- 原文行号。
- 完整 Markdown 原文。
- 识别原因，例如“Markdown 复选框”或“普通列表，仅作为候选”。
- 是否默认选中。
- 拟导入的标题、详情、状态、开始日期、截止日期、四象限、项目和标签。

用户可以选择候选并修正所有拟导入字段。普通列表不能因为置信度或标记文字自动选中。

## 6. 三步导入向导

### 6.1 第一步：选择文件

- 只展示配置扫描目录内的 Markdown 文件。
- 支持多选。
- 显示 Vault 相对路径，避免同名文件混淆。
- 未选择文件时不能继续。

### 6.2 第二步：核对候选

- 候选按来源文件分组。
- 文件标题显示候选总数和已选数量。
- 每条候选优先展示标题、原文位置、识别原因和选中状态。
- 展开候选后编辑完整字段。
- 前后切换步骤时保留选中状态和字段修正。
- 单个文件读取或解析失败时显示在对应文件旁，不阻止审阅其他成功文件。

### 6.3 第三步：确认修改

确认页汇总：

- 来源文件列表。
- 每个文件的选中数量。
- 复选框候选与手动选择普通列表的数量。
- 写入方式：在各自原文件中替换所选原文。
- 备份路径。
- 未选择内容保持不变的明确说明。

只有最终确认按钮会触发写入。关闭、取消、返回上一步或只查看预览都不得修改 Vault。

## 7. 组件与服务边界

### 7.1 界面组件

- `WorkspaceHeader`：标题、主操作和任务/日历模式导航。
- `TaskFilterBar`：搜索、筛选胶囊、筛选弹出选择和清除筛选。
- `TaskFormModal`：分组单栏表单、折叠归档字段和固定操作区。
- `LegacyImportWizard`：管理三步状态、文件选择、候选修正和最终确认。

组件名称可以按现有代码风格调整，但职责必须保持独立，避免继续扩大单个工作区渲染函数。

### 7.2 迁移服务

迁移拆为两个明确边界：

- 候选识别器：输入用户选择的路径和 Markdown 内容，输出带来源证据的候选；不写文件。
- 安全写入器：输入最终选中和修正后的候选，完成校验、备份、冲突检测、写入、验证、回滚和索引刷新。

写入器继续保持现有保护：

- 所有选中候选先完成领域校验，再产生任何文件副作用。
- 每个被修改的源文件先备份。
- 预览后源文件发生变化时拒绝写入并要求重新核对。
- 只替换选中的原文范围。
- 写入后重新解析，确认任务存在、未选原文未变化且无解析问题。
- 写入或验证失败时恢复原文。

## 8. 错误处理

- 文件选择失败：停留在第一步并标记具体路径。
- 文件读取或候选解析失败：第二步按文件展示错误，其他文件仍可继续。
- 候选字段无效：错误显示在对应候选的具体字段，阻止进入最终确认。
- 备份、并发冲突、写入或验证失败：向用户说明失败文件和原因，不显示模糊的通用成功提示。
- 向导处于提交状态时锁定选择、编辑、步骤导航和确认按钮，避免重复提交。

## 9. 验收与测试

### 9.1 工作区与表单

- 明暗主题中无硬编码导致的不可读文字或背景。
- 宽窄布局下标题、模式、搜索和筛选层级正确。
- 每个筛选条件可改变结果，清除筛选恢复默认状态。
- 搜索重渲染后保持焦点与光标。
- 新建默认值符合规范。
- 编辑允许清空可选字段。
- 多行详情、日期格式和四象限约束均有回归测试。

### 9.2 旧任务导入

- 未选择文件时不执行扫描。
- 只读取明确选择的文件。
- 复选框默认选中，普通列表默认不选中。
- 普通正文即使包含 `P0-P4` 或状态文字也不会成为候选。
- 候选包含来源路径、行号、原文和识别原因。
- 三步前后切换保持选择与修正。
- 取消任何一步不写文件。
- 备份、并发冲突、写入验证、失败回滚和重复导入防护通过测试。
- 使用当前 Vault 旧任务结构制作脱敏 fixture，覆盖日期标题、普通列表、编号列表、状态文字和优先级文字混排。

## 10. 不在本轮范围

- 改变标准任务 Markdown 格式。
- 引入数据库或其他任务事实源。
- 自动迁移整个 Vault。
- 保存筛选视图或创建复杂查询语言。
- 多级子任务或项目管理扩展。

## 11. 完成标准

本轮完成必须同时满足：

1. 工作区、任务弹窗和导入向导符合已确认的视觉与交互方向。
2. 用户能在导入前明确回答“数据来自哪个文件、哪一行、为什么被识别、会修改什么”。
3. 未经最终确认不修改 Markdown。
4. 全量测试、覆盖率、Lint 和生产构建通过。
5. 安装到主 Vault 前备份现有插件，安装后核验产物哈希并做不写入旧任务的交互冒烟测试。
